# Чек-лист проверки десктоп-приложения отображения сигналов

**Объект:** десктоп-клиент + TCP-сервис-симулятор (порт 2001)  
**Охват:** smoke / критичный функционал (не более 15 пунктов)

| # | Приоритет | Проверка | Ожидаемый результат |
|---|-----------|----------|---------------------|
| 1 | Critical | Запуск приложения | Главное окно открывается без ошибок |
| 2 | Critical | Состав UI | Видны таблица сигналов и кнопки «Подключиться», «Обновить» |
| 3 | Critical | Колонки таблицы | Есть столбцы: ID, имя, значение, качество, время |
| 4 | Critical | Подключение при работающем симуляторе (порт 2001) | Соединение устанавливается, индикация успеха (если есть) |
| 5 | Critical | Получение сигналов после подключения | В таблице ровно **10** строк сигналов |
| 6 | Critical | Структура данных сигнала | У каждой строки заполнены ID, имя, значение, качество, время |
| 7 | High | Кнопка «Обновить» | Значения/время в таблице обновляются после запроса |
| 8 | High | Изменение значений во времени | Значения меняются (синусоида / случайные), таблица отражает изменения |
| 9 | Critical | Симулятор недоступен (порт закрыт) | Ошибка/статус «нет связи», приложение не падает |
| 10 | High | «Обновить» без активного соединения | Запрос не выполняется или показывается ошибка; UI остаётся стабильным |
| 11 | High | Повторное подключение | Повторный connect / reconnect не приводит к дублям строк и зависанию |
| 12 | Medium | Корректность качества | Поле «качество» принимает ожидаемые значения (например good/bad/uncertain) |
| 13 | Medium | Актуальность времени | Метка времени обновляется при получении новых данных |
| 14 | Medium | Стабильность при частых обновлениях | UI не зависает, данные остаются консистентными |
| 15 | Medium | Закрытие приложения при активном соединении | Сокет корректно закрывается, процесс завершается без зависания |

## Самый критичный сценарий

**Пункты 4–6: успешное подключение к сервису и получение всех 10 сигналов с полной структурой данных.**

### Почему именно он

1. **Бизнес-смысл приложения** — показывать оператору актуальные сигналы с удалённого сервиса. Без установления TCP-соединения и получения данных остальной UI бесполезен.
2. **Риск регрессии высокий** — ошибка в протоколе, парсинге или порту сразу ломает весь мониторинг.
3. **База для остальных проверок** — обновление, качество, время, reconnect имеют смысл только если happy-path «connect → 10 сигналов» уже работает.
4. **Хорошо автоматизируется** — сценарий детерминирован на уровне TCP и даёт чёткие assert’ы без зависимости от визуальных нюансов UI.
